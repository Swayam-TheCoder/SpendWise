login flow:

POST /api/auth/login
        ↓
Validate input
        ↓
Find user by email
        ↓
Get hashed password
        ↓
Argon2.verify()
        ↓
Update lastLoginAt
        ↓
Create authentication tokens
        ↓
Set secure HTTP-only cookies
        ↓
Return user


we split it in 2 parts:
1st part: Verify credentials
email + password
       ↓
find User
       ↓
verify Argon2 hash
       ↓
login successful

2nd part: Authentication tokens
Access Token
Refresh Token
HTTP-only cookies
Session table
Token rotation
Logout


Access Tokens + Refresh tokens
Access Token
→ short-lived
→ used for API authorization

Refresh Token
→ long-lived
→ used to obtain a new access token
→ stored as a hash in PostgreSQL
→ sent through HTTP-only cookie


Why hash the refresh token?
we dont want this in postgresql

refreshTokenHash -> actual JWT

instead: 
 Refresh Token
     ↓
   SHA-256
     ↓
   Hash
     ↓
 PostgreSQL

SHA-256 is a cryptographic hash function that turns any input text or file into a unique, fixed 256-bit (64-character hexadecimal) digital fingerprint

here, If someone gets database access, they shouldn't immediately get usable refresh tokens.
